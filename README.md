# prec-bsl

`prec-bsl` - Rust-пакет hook'ов для [`prek`](https://prek.j178.dev/) и
[`pre-commit`](https://pre-commit.com/) в проектах 1C, где BSL, Designer XML и
EDT-источники хранятся в Git.

Цель проекта - сохранить привычную механику [`precommit4onec`](https://github.com/bia-technologies/precommit4onec) для
[встроенного v1-набора сценариев](spec/reference-scenario-inventory.md), но
убрать обязательную зависимость от OScript в обычном пути выполнения hook'а.
`prec-bsl` читает staged-файлы из Git index, запускает встроенные проверки и
фиксаторы, явно сообщает об изменениях и, когда файл был исправлен, передает
restaging в отдельный Git-слой.

## Что делает

- публикует hook `prec-bsl` через
  [`.pre-commit-hooks.yaml`](.pre-commit-hooks.yaml);
- запускается из [`prek`](https://prek.j178.dev/) /
  [`pre-commit`](https://pre-commit.com/) как Rust hook;
- в commit-режиме использует Git index, а не список файлов от runner'а;
- читает настройки из [`v8config.json`](spec/configuration.md), включая
  совместимый ключ `Precommt4onecСценарии`;
- поддерживает команды `check` (диагностика без записи) и `fix` (применение
  фикстеров, `--dry-run` для предпросмотра, `--restage` для рестейджа) с
  режимами выбора файлов `--mode all|changed|index|worktree`;
- поддерживает запуск выбранных правил по source root'ам через устаревшую
  `exec-rules` (алиас `fix --mode all`);
- классифицирует BSL, Designer XML, EDT `.mdo` / `.form` и внешние
  `.epf` / `.erf` / `.cfe` артефакты;
- выводит детерминированный результат в `text` или `json`.

## Установка через prek

Добавьте hook-репозиторий в
[`prek.toml`](https://prek.j178.dev/configuration/) потребляющего проекта:

```toml
[[repos]]
repo = "https://github.com/alkoleft/prec-bsl"
rev = "v0.1.5"

[[repos.hooks]]
id = "prec-bsl"
args = ["--config", "v8config.json"]
```

Манифест репозитория запускает hook как:

```text
prec-bsl prek-hook
```

Hook объявлен как `language: rust`, `always_run: true` и
`pass_filenames: false`. Это важно: contract commit-режима строится вокруг
staged Git index, включая удаления и Git-статусы, а не вокруг фильтрации файлов
со стороны `prek`.

## Установка через pre-commit

Тот же hook можно подключить из
[`.pre-commit-config.yaml`](https://pre-commit.com/#2-add-a-pre-commit-configuration):

```yaml
repos:
  - repo: https://github.com/alkoleft/prec-bsl
    rev: v0.1.5
    hooks:
      - id: prec-bsl
        args:
          - --config
          - v8config.json
```

В hook args стоит оставлять только небольшие стабильные CLI-настройки:
`--config`, `--source-dir`, `--rules`, `--format`, `--ignore-merge-commit`,
`--ignore-remote-merge-commit`.
Сценарии, project-specific
переопределения и большие настройки должны жить в `v8config.json`.

## Команды

Commit hook mode:

```text
prec-bsl prek-hook [--config <path>] [--source-dir <path>] [--rules <list>] [--format text|json] [--ignore-merge-commit|--ignore-remote-merge-commit]
```

Этот режим используется hook'ом. Он определяет корень Git-репозитория, читает
staged-файлы через `git diff --name-status --staged --no-renames`, запускает
настроенные сценарии и явно сообщает о modified paths. Если `--source-dir` не
указан, source roots определяются по `v8project.yaml` `source-set`, а при
отсутствии manifest - по staged-файлам и ближайшим
`Configuration/Configuration.mdo` или `Configuration.xml`.
С `--ignore-merge-commit` режим выходит с кодом `0`, когда Git сообщает
активное merge-состояние через `MERGE_HEAD`, и не запускает проверки,
фиксаторы или restaging. С `--ignore-remote-merge-commit` skip применяется
только когда хотя бы один SHA из `MERGE_HEAD` достижим из `refs/remotes/*`.
Оба merge-ignore флага нельзя указывать одновременно.

Проверка без изменения файлов:

```text
prec-bsl check <repo> [--config <path>] [--source-dir <list>] [--rules <list>] [--format text|json] [--mode <m>]
```

`check` только диагностирует нарушения и никогда не пишет в файлы: фиксеры
прогоняются в памяти, и для каждого файла с изменениями выводится построчный
дифф `+`/`-` («Предлагаемые изменения (не записаны)»; в формате `json` дифф не
печатается — Proposed-контент уже есть в поле `proposed_content` каждого
результата). «Нарушение» - это ситуация, когда фиксер изменил бы файл, либо
диагностическое сообщение checker-сценария (включая предупреждения — например,
найденные нецензурные слова). Коды выхода: `0` - нарушений нет, `1` - есть
нарушения, `2` - ошибка выполнения.

Предупреждения в `check`/`fix` считаются нарушениями (exit 1). Hook-режим
(`prek-hook`) в этом отличается намеренно: там предупреждение не блокирует
коммит (контракт precommit4onec), а блокируют только ошибки и незаревьюенные
правки фиксеров.

Применение фикстеров:

```text
prec-bsl fix <repo> [--config <path>] [--source-dir <list>] [--rules <list>] [--format text|json] [--mode <m>] [--dry-run] [--restage]
```

`fix` применяет фиксеры к файлам. `--dry-run` показывает, что изменилось бы
(построчный дифф по каждому файлу в text-формате), не записывая изменения.
`--restage` после применения правок добавляет исправленные файлы в Git index —
тот же restaging-шаг, который выполняет `prek-hook`. Коды выхода:
`0` - правок не потребовалось, `1` - правки применены (в dry-run: есть что
применять) или есть диагностические сообщения (включая предупреждения),
`2` - ошибка.

`--restage` вместе с `--dry-run` — не ошибка, а предупреждение в stderr:
restage не имеет смысла без записи, dry-run выполняется как обычно, файлы и
индекс не трогаются. Так сделано намеренно, чтобы не ломать скрипты, в которых
флаг `--restage` стоит постоянно.

Режимы `--mode` (по умолчанию `all`) выбирают набор файлов:

- `all` - все исходники в source roots (эквивалент исторического `exec-rules`);
- `changed` - всё изменённое относительно `HEAD`: staged + unstaged + untracked
  (новые файлы включаются);
- `index` - только staged (тот же Git-слой, что использует `prek-hook`);
- `worktree` - изменённые вне индекса: unstaged + untracked.

Файлы режима пересекаются с source roots и классификацией типов: не-исходники
отфильтровываются как обычно, удалённые файлы (статус `D`) пропускаются с
сообщением «сценарий не обрабатывает удаленные файлы».

### Семантика режимов относительно staged-контента

Все режимы `check`/`fix` читают и правят (в `fix`) **рабочую копию** файлов на
диске. Staged-контент (Git index) никогда не перезаписывается молча.

`--mode` — это фильтр **выборки** файлов по Git-статусу, а не выбор версии
контента: `--mode index` выбирает staged-файлы, но анализирует и исправляет их
текущее содержимое в рабочей копии, а не версию из индекса.

`--restage` — единственный способ попросить `prec-bsl` записать исправленный
контент обратно в индекс (аналог restaging-обвязки `prek-hook`). По умолчанию
(без флага) `fix` правит только рабочую копию и индекс не трогает — это
обратно совместимо с любыми существующими скриптами.

Пример на файле со статусом `MM` (staged-версия и рабочая копия обе содержат
нарушение, например лишние концевые пробелы):

| Команда | Рабочая копия | Staged (index) | Статус после |
| --- | --- | --- | --- |
| `fix --mode index` | исправлена | не тронута: нарушение остаётся | `MM` (staged-часть всё ещё отличается от `HEAD`, а исправленная рабочая копия теперь отличается от индекса) |
| `fix --mode index --restage` | исправлена | исправлена (исправленное попало в индекс) | чисто относительно `HEAD` |

```bash
# исправить staged-файлы и обновить индекс перед коммитом
prec-bsl fix . --mode index --restage

# проверить, что изменится, без записи и без рестейджа
prec-bsl fix . --mode worktree --dry-run
```

Примеры:

```bash
# проверка только изменённых файлов перед коммитом
prec-bsl check . --mode changed --rules УдалениеЛишнихКонцевыхПробелов

# применить фиксеры ко всем исходникам репозитория
prec-bsl fix . --mode all

# посмотреть, что изменил бы фикс, без записи
prec-bsl fix . --mode worktree --dry-run
```

Устаревшая команда (deprecated):

```text
prec-bsl exec-rules <repo> [--config <path>] [--source-dir <list>] [--rules <list>] [--format text|json]
```

`exec-rules` устарела и сохранена как алиас `fix --mode all`: при запуске
выводит предупреждение в stderr, поведение и коды выхода полностью сохранены
(включая запись файлов) для обратной совместимости. Используйте
`prec-bsl fix --mode all`.

Этот режим удобен для CI, миграционной проверки и ручного запуска выбранных
правил. `--source-dir` и `--rules` принимают списки через запятую. Если
`--source-dir` не указан, `exec-rules` использует source roots из
`v8project.yaml` при его наличии; без `v8project.yaml` остается запуск от корня
репозитория.

Пример:

```bash
prec-bsl exec-rules . \
  --source-dir fixtures/configuration/src,exts/rat/src \
  --rules УдалениеЛишнихКонцевыхПробелов,ПроверкаКорректностиОбластей
```

JSON-вывод:

```bash
prec-bsl check . --rules ПроверкаКорректностиОбластей --format json
```

## Конфигурация

Основной domain-config - [`v8config.json`](spec/configuration.md) в корне
репозитория. Порядок приоритета:

1. CLI-аргументы hook'а или ручного запуска.
2. `v8config.json`.
3. Встроенные значения по умолчанию.

`v8config.json` необязателен. Если файл отсутствует, в том числе при типовом
`args = ["--config", "v8config.json"]`, `prec-bsl` запускает встроенный v1-набор
сценариев с настройками по умолчанию.

Семантика ключа `ГлобальныеСценарии`:

- ключ отсутствует — используется встроенный v1-набор (тот же список, что и при
  отсутствии `v8config.json` целиком);
- ключ равен `[]` — осознанное отключение всех сценариев;
- ключ содержит список — включаются перечисленные сценарии.

То же правило действует для секций `Проекты`: проект без собственного ключа
`ГлобальныеСценарии` наследует набор корневой секции (а при его отсутствии —
встроенный v1-набор); явный пустой массив в секции проекта отключает сценарии
только для этого проекта. `ОтключенныеСценарии` вычитаются из итогового набора
на любом уровне.

Минимальный пример:

```json
{
  "GLOBAL": {
    "version": "2.0",
    "ФорматEDT": true,
    "ВерсияПлатформы": ""
  },
  "Precommt4onecСценарии": {
    "ИспользоватьСценарииРепозитория": false,
    "КаталогЛокальныхСценариев": "",
    "ГлобальныеСценарии": [
      "УдалениеЛишнихКонцевыхПробелов.os",
      "ПроверкаКорректностиОбластей.os"
    ],
    "ОтключенныеСценарии": [],
    "НастройкиСценариев": {}
  }
}
```

Историческое написание `Precommt4onecСценарии` сохранено намеренно для
совместимости с `precommit4onec`.

## Поддержанные v1-сценарии

Встроенный v1-набор покрывает
[required-сценарии из спецификации](spec/reference-scenario-inventory.md):

- `ВставкаКопирайтов`
- `ДобавлениеПробеловПередКлючевымиСловами`
- `ЗапретИспользованияПерейти`
- `ИсправлениеНеКаноническогоНаписания`
- `КорректировкаXMLФорм`
- `ОтключениеПолнотекстовогоПоиска`
- `ОтключениеРазрешенияИзменятьФорму`
- `ПроверкаДублейПроцедурИФункций`
- `ПроверкаКорректностиИнструкцийПрепроцессора`
- `ПроверкаКорректностиОбластей`
- `ПроверкаНецензурныхСлов`
- `РазборОтчетовОбработокРасширений`
- `СинхронизацияОбъектовМетаданныхИФайлов`
- `СортировкаСостава`
- `УдалениеДублейМетаданных`
- `УдалениеЛишнихКонцевыхПробелов`
- `УдалениеЛишнихПустыхСтрок`

Для миграции существующих `precommit4onec` конфигураций дополнительно
поддержаны явные compatibility-сценарии:

- `СортировкаДереваМетаданных`
- `СортировкаСоставаПодсистем`

Помимо v1-набора доступны extension-сценарии (opt-in через
`ГлобальныеСценарии` / `--rules`, см.
[спецификацию инвентаря](spec/reference-scenario-inventory.md)):

- `ПробелыВКомментариях`, `ПробелыПослеЗапятых` — лексические фиксеры
  (bsl-ls SpaceAtStartComment / MissingSpace-подмножество);
- `ПроверкаДлиныСтрок` — check-only диагностика длинных строк (bsl-ls
  LineLength): лимит по умолчанию 150, настраивается через
  `НастройкиСценариев.ПроверкаДлиныСтрок.МаксимальнаяДлинаСтроки`; правило
  считает длину в символах без хвостовых пробелов и строк-продолжений
  многострочных литералов; правила переноса длинных строк описаны в
  [`spec/line-break-rules.md`](spec/line-break-rules.md);
- `ОдинОператорНаСтроку` — check+fix: диагностика и разбиение строк с
  несколькими операторами (bsl-ls OneStatementPerLine), фикс переносит
  оператор на отдельную строку с отступом строки, а оператор после
  `Тогда`/`ИначеЕсли ... Тогда` — со сдвигом +1 таб внутрь блока; контракт —
  в [`spec/parser-strategy.md`](spec/parser-strategy.md).

Имена можно указывать с суффиксом `.os` или без него. Эти сценарии выполняются
как встроенная Rust XML/EDT-обработка: первый сортирует состав дерева метаданных
в `Configuration.mdo` / `Configuration.xml`, второй сортирует состав подсистем
в EDT `.mdo` и Designer `.xml` описаниях подсистем. Это не включает общий
запуск repository-local `.os` сценариев.

BSL-сценарии, которым нужна синтаксическая структура, используют
[`tree-sitter-bsl`](https://docs.rs/tree-sitter-bsl/latest/tree_sitter_bsl/).
Текстовые parity-фиксаторы остаются лексическими там, где главный contract -
точное сохранение текста.

XML/EDT-сценарии используют структурный XML-слой, а не широкие regex-rewrite'ы.

## Явные ограничения v1

- `РазборОбычныхФормНаИсходники` не реализуется по продуктовому решению.
  Если сценарий включен в `v8config.json`, конфигурация должна завершиться
  понятной ошибкой.
- `ОбработкаЮнитТестов` удален из поддержанного v1-набора. Если сценарий
  включен в `v8config.json`, конфигурация должна завершиться понятной ошибкой.
- Repository-local `.os` сценарии не выполняются в v1. Включенные локальные или
  неизвестные сценарии должны давать явную unsupported-диагностику.
- `РазборОтчетовОбработокРасширений` зарегистрирован как required-сценарий, но
  имеет отдельную runtime-границу: для реального разбора внешних
  отчетов/обработок/расширений нужна 1C platform runtime. Обычный Rust hook не
  запускает 1C скрыто.

## Поведение hook'а

Hook mode возвращает `0` только когда нет blocking diagnostics и не осталось
непросмотренных изменений. Если фиксер изменил файл, путь будет показан в
отчете, файл будет явно restaged Git-слоем, а пользователь должен увидеть
результат и повторить проверку при необходимости.

Форматы вывода:

- `text` - человекочитаемый отчет по правилам и файлам;
- `json` - структурированный отчет для CI и внешних инструментов.
